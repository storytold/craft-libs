# Code Style & Quality Lints

This document outlines the compiler lint rules, formatting conventions, and clean-room policies for `craft-libs`.

---

## 1. Toolchain & Workspace Standards

- **Rust Edition**: 2024
- **Cargo Resolver**: Version 3
- **Minimum Supported Rust Version (MSRV)**: 1.95
- **Monorepo Inheritance**:
  All workspace crates inherit package metadata and lints from the workspace root:
  ```toml
  [package]
  edition.workspace = true
  license.workspace = true
  rust-version.workspace = true

  [lints]
  workspace = true
  ```

---

## 2. Formatting Standards (`rustfmt.toml`)

All code must format cleanly using `rustfmt`:

```toml
max_width = 150
use_small_heuristics = "Max"
```

- **Imports**: Group imports: `std::`, external dependencies, workspace crates, and internal module paths.
- **Trailing Commas**: Use trailing commas in multiline structs, enum definitions, and argument lists to minimize diff noise.

---

## 3. Strict Quality Lints & Never-Crash Policy

Every crate root (`src/lib.rs`) must explicitly enforce:

```rust
#![deny(
    clippy::unwrap_used,
    clippy::expect_used,
    clippy::panic,
    clippy::unimplemented,
    clippy::todo,
    clippy::unreachable
)]
```

### Compiler Warnings
Compiler warnings are treated as build failures:
```bash
cargo clippy --workspace --all-targets -- -D warnings
```

### Test Scope Exceptions
Unit and integration tests may use indexing and unwrapping for test brevity via `clippy.toml`:
```toml
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests = true
allow-indexing-slicing-in-tests = true
```

---

## 4. Unsafe Code Forbidden

Unsafe code is strictly forbidden across all shared library crates:
```rust
#![forbid(unsafe_code)]
```

---

## 5. Concurrency Safety

- **Mutex Poisoning Recovery**:
  Never panic when acquiring mutexes. Gracefully recover from poisoned locks:
  ```rust
  let mut guard = mutex.lock().unwrap_or_else(PoisonError::into_inner);
  ```
- **Thread Joins**:
  Treat thread joins as fallible results; propagate errors rather than panicking on termination.

---

## 6. Clean-Room Governance & Asset Policy

- **Dual-Licensing**: All shared library code is dual-licensed under **MIT OR Apache-2.0**.
- **Clean-Room Specification Boundary**:
  - Implementations must be derived exclusively from published standards (ISO 32000, ICC.1, SMPTE, Unicode, W3C) and observable behavior.
  - Never decompile or copy proprietary code, shaders, or presets from Adobe, Autodesk, Avid, or Microsoft.
  - Never copy or link copyleft code (GPL/LGPL/AGPL).
- **Attribution**: Every bundled asset must be recorded in `ATTRIBUTION.md`.
- **Font Policy**: Font binaries are never committed to git; fonts live in [`storytold/craft-fonts`](https://github.com/storytold/craft-fonts) via `CRAFT_FONTS_DIR`.
- **Test Corpora**: Large test fixtures belong in external corpora [`storytold/photocraft-corpus`](https://github.com/storytold/photocraft-corpus).

## 8. Tickets, PRs, Commits & Squash Merging

### 8.1 Issues & Ticket Etiquette
- **Claim Before You Start**: Always comment on an existing issue or open a proposal before starting work.
- **Structure**: Every ticket must articulate the problem statement, proposed architectural design, and an actionable checkbox acceptance list (`- [ ]`).

### 8.2 Commit Message Formatting
- **Subject**: 50–72 characters, imperative present tense (*"Add..."*, *"Fix..."*, *"Extract..."*, *"Preserve..."*). Capitalized, no period.
- **Issue Reference**: End subject or body of target/squash commits with tracking tags: `(refs #37)` or `(fixes #7)`. **Never reference issues in intermediate scratch commits** pushed to remote branches; GitHub records an immutable timeline cross-reference for every pushed commit containing an issue tag, cluttering the issue thread even after the branch is squashed.
- **Body**: Detailed explanation of *why* the change was made and how boundaries are protected, wrapped at 72–80 characters.

### 8.3 Pull Request Structure
- **Title**: Imperative summary matching the squash commit: `Verb in imperative mood: short description (closes #XX)`.
- **Body**: Concise summary, bulleted change log, concrete verification evidence (exit codes, test counts, WASM checks), and adherence to the Four-Tier Claim Taxonomy.

### 8.4 Squash Merging Strategy
- Pull requests are integrated into `main` via **Squash and Merge** to maintain a clean, linear, bisectable Git history.
- The squash commit subject defaults to `<PR Title> (#<PR Number>)` with a curated commit body containing the PR summary and issue closure tag (`Closes #XX`). Scratch commits (*"wip"*, *"fix typo"*) are squashed out.

### 8.5 Review Comments & Technical Communication
- Evidence-first: Anchor comments in specific file paths, line numbers, compiler output, or minimal reproductions.
- Grounded references: Never make unreferenced claims like *"the work I have been doing"*. Always link directly to the exact pull request, commit, or issue (e.g. `[storytold/craft-libs#9](https://github.com/storytold/craft-libs/pull/9)`).
- Constructive: Propose preferred patterns (e.g. `.get()` or rich domain error variants) when pointing out issues.
- Natural style: Direct, active engineering prose without promotional filler, assistant identity markers, or stylistic tells like em-dash (`—`) crutches.
- Small-batch landings: Favor small, focused, bisectable pull requests over massive multi-feature monoliths.
